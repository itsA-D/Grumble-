# Architecture

How Grumble (Go) is organised, where things live, and which rules the design must never break. Product intent is in `PRD.md` (requirement IDs such as FR-VOTE-1 are referenced below). Agent instructions are in `CLAUDE.md`.

This file is deliberately short and stable. It names things instead of linking to them: use symbol search or `rg` to find an entity by name. Revisit it a couple of times a year, not on every change. Decisions that change this file are recorded as ADRs in `docs/adr/`.

The module path is written `github.com/OWNER/Grumble` throughout; replace `OWNER` once, in `go.mod`, before the first commit. The product name is a config value, never hard-coded.

## 1. Bird's-eye view

Grumble is a public board where anyone posts a short frustration, others vote, and the system scores each pain for urgency. Public pages (feed, trending, map, category, country and keyword hubs, pain pages) are rendered on the server so search engines see content. A paid layer (money feed, AI briefs, exports, alerts) reads the same data.

One Postgres database is the source of truth. Everything else is a view of it or a job that writes back to it. It is a **modular monolith**: one codebase, one deployable image, no microservices, no message broker.

```
Browser ──► transport/web (chi + templ + HTMX) ──► service ──► domain, scoring (pure)
   ▲                │                                  │
   │ SSE            ├─► platform adapters ──────────────┤
   │                │   (llm, email, billing, turnstile,│
   │                │    ratelimit, cache, clock, idgen)│
   │                │                                  ▼
   │                │                             store/postgres (pgx + sqlc) ──► Postgres
   │                └─► river queue (jobs, in the same DB) ──────────▲
   └────────────── platform/realtime ◄── LISTEN/NOTIFY ──────────────┘
```

Anonymous visitors can read, submit, vote, comment and bookmark. Signed-in users add alerts, exports and Pro features. The same binary runs `serve` and `worker`; one process does both by default, and a flag splits them so the worker can scale on its own.

## 4. Module map

Each capability under `internal/service/` is a module with a small public API (an interface plus request and result types). Modules call each other through that API or react to in-process events; they never reach into another module's repositories or tables. Only the owning module writes its tables; read-only modules (`hubs`, `map`, `admin`) may run dedicated read queries across tables and never write.

| Module | Responsibility |
| --- | --- |
| `pains` | Create pains, slugs, status transitions, read lists and details |
| `moderation` | Rule checks, PII detection, model classification, flags, admin actions, audit log |
| `voting` | Cast and remove votes, velocity checks, source clustering |
| `comments` | Comments through the same pipeline and limits as pains |
| `bookmarks` | Save and limit bookmarks; anonymous-to-user merge |
| `hubs` | Hub queries, counts, intro and FAQ copy, indexability rule |
| `identity` | Anonymous-id cookie, `source_hash`, merge on sign-in |
| `briefs` | Prompt assembly, grounding check, generation, cache |
| `alerts`, `digest`, `newsletter` | Alert matching, digest assembly, double opt-in email |
| `billing` | Plans, checkout, webhook verification, entitlements |
| `exports` | CSV and PDF generation |
| `admin` | Metrics queries, role checks |
| `realtime`, `map` | SSE hub, batcher, listener; `country_stats` read model |

`internal/domain` and `internal/scoring` import nothing from this module's other packages and do no I/O. `service` declares the small interfaces it needs (repository, clock, mailer); `store` and `platform` implement them and are injected through constructors. No globals, no `init()` side effects, no singletons.

## 5. Data model

Defined only in `db/migrations/`, forward-only, never edited after merge. Tables are added in the phase that first uses them; Phase 0 ships the baseline migration and the schema bookkeeping only.

| Table | Purpose | Added in |
| --- | --- | --- |
| `pains` | One submission | M1 |
| `votes` | One vote; unique (`pain_id`, `voter_key`) | M1 |
| `comments` | Short comment | M2 |
| `flags` | Report | M2 |
| `bookmarks` | Saved pain; `owner_key`, `pain_id` | M2 |
| `profiles` | Account: `user_id`, `role`, `plan`, `plan_status` | M3 |
| `subscribers` | Email list: `email`, `list`, `confirmed_at`, `unsubscribed_at` | M2 |
| `briefs` | Cached AI brief: `pain_id`, `model`, `body`, `signals_hash` | M3 |
| `alerts` | Saved alert rule | M3 |
| `moderation_log` | Audit trail: `target`, `actor`, `action`, `reason`, `created_at` | M2 |
| `scoring_versions` | Weight history | M1 |
| `stats` | Single-row counters | M2 |
| `country_stats` | Map read model: `country`, `category NULL`, `pain_count`, `avg_urgency` | M2 |
| `sessions` | `scs` session store | M3 |
| `magic_link_tokens` | Hash only, single use, short expiry | M3 |
| `processed_webhook_events` | Idempotency for billing webhooks | M3 |
| River tables | Queue, runs, periodic jobs | M1 (worker) |

`status` on `pains` and `comments` is one of `pending`, `published`, `held`, `rejected`, `removed`. `voter_key` and `owner_key` are `u:<user_id>` for signed-in users and `a:<anon_id>` otherwise. Constraints do real work: check constraints on enums and lengths, foreign keys, NOT NULL by default, indexes for every feed and hub query (category, country, status, created_at, urgency, vote_count), GIN on the search vector.

Counters (`vote_count`, `urgency`, `stats`) are **not** maintained by database triggers. They are updated in the same transaction as the change, through the pure `scoring` package (invariant 6). A nightly job recomputes them absolutely, so running it twice changes nothing.

## 6. Key flows

### Submit

1. The submit form posts to a thin handler that validates the request and checks the rate limit by `source_hash` and anonymous id.
2. `pains.create` runs in one transaction: insert with status `pending`, run rule checks and PII detection, set `published` or `held` or `rejected`, update counters through `scoring`, and enqueue the classification job **in the same transaction** (no lost events).
3. Publishing fires an in-process event after commit; the batcher coalesces it and the SSE stream notifies open pages.

### Vote

`voting.Cast` runs `InsertVote ... ON CONFLICT DO NOTHING` inside a `TxManager` transaction; if a row was added it increments `vote_count`, reads signals, and writes `urgency` from the pure function. A repeat vote is a no-op; the toggle path deletes. The UI updates optimistically and reconciles with the response and the SSE `votes.changed` event.

### Render a hub

A hub page calls `hubs.get(kind, slug)` for the count, ranked pains and original copy. `hubs.isIndexable` decides robots meta and sitemap membership (5-pain threshold, FR-SEO-3). Pages send `Cache-Control` with `s-maxage` and `stale-while-revalidate` so a CDN between us and the reader serves cached HTML.

### Upgrade to Pro

`/pro` creates a checkout session through `billing`. The provider calls `/webhooks/billing`; the handler verifies the signature (constant-time) and the event id, then writes `profiles.plan` and `plan_status`. The browser is never trusted to say it paid.

### AI brief

`briefs.get(painID)` returns the cached brief when its `signals_hash` matches the current signals, else assembles a prompt from stored fields only, calls the model behind an interface, runs the grounding check, caches and returns. With fewer than three signals it returns "not enough signal" without calling the model. Always labelled AI-generated.

## 7. Background jobs

River runs in the same database. Jobs are idempotent: each recomputes an absolute value from current data.

| Job | Cadence | Does |
| --- | --- | --- |
| `moderation-sweep` | every 5 min | Retry unclassified pending items; escalate stale held items |
| `hot-rank` | every 10 min | Refresh trending ranks |
| `country-stats` | ~1 min | Rebuild the `country_stats` read model; emit `map.updated` |
| `alerts` | hourly | Match new or spiking pains to alert rules |
| `digest-free` | Sunday 08:00 UTC | Top 3 of the week |
| `digest-pro` | Monday 08:00 UTC | 5 picks with briefs |
| `retention` | daily | Delete expired rate-limit data, rotate the hash salt monthly, apply deletion requests, recompute counters |

## 8. Architectural invariants

Rules the code must keep. Several are absences, which cannot be seen by reading one file.

1. **Clients never write to the database.** The database is private, reached only by the app with one role; there is no public database API. All writes run in `service` through `store/postgres`.
2. **Dependency direction:** `transport` → `service` → `domain`; `scoring` and `domain` import nothing from the module and do no I/O. `store` and `platform` implement interfaces their consumer declares. Enforced by an import-boundary check in CI, not by docs alone.
3. **Public reads see only `status = 'published'`**, through dedicated repository methods and a `published_pains` view; tests prove unpublished rows never leak. This replaces RLS (see ADR 0001).
4. **Never store a raw IP address.** Compute a salted `source_hash` from the client address and rotate the salt monthly (NFR-PRIV-1). Take the client address only from the configured trusted-proxy header.
5. **User text is plain text, escaped by templ** everywhere — HTML, email and share images (NFR-SEC-4).
6. **Counters and `urgency` update in the same transaction as the change, through the pure `scoring` package.** No business logic in database triggers.
7. **Prices, plan names and entitlements exist only in `internal/domain/billing/plans.go`.**
8. **Scoring weights live only in `internal/scoring/weights.go` and `scoring_versions`.** Nothing hard-codes a weight.
9. **Entitlements change only from a verified billing webhook.**
10. **Provider SDKs (model, email, billing, Turnstile) are imported only inside their `internal/platform` adapter.** Each adapter has a fake for tests and a log-only implementation for local development.
11. **AI briefs use stored signals only and are always labelled AI-generated.** Pains are never AI-written.
12. **Counts of zero never appear in page titles or meta descriptions.**
13. **Every moderator action writes `moderation_log` in the same transaction.**
14. **Webhook and job handlers are safe to run twice** (store processed event ids).

## 9. Boundaries

| Boundary | Contract |
| --- | --- |
| Browser and server | Request and response types beside each handler/service; the browser sees HTML and JSON, never database shapes |
| Service and storage | A `TxManager` (unit of work) runs a function in one transaction; services never manage `pgx.Tx` directly |
| Service and providers | One adapter per provider behind an interface the service declares; tests use fakes |
| Public and admin | `/admin/*` requires a role and recent re-auth, and is excluded from indexing and caching |
| Module and module | Module APIs carry no database or HTTP types, so a module could later move behind a network call |

## 10. Cross-cutting concerns

- **Identity.** Anonymous id is a signed, httpOnly, SameSite=Lax cookie (Secure in production). On sign-in, votes and bookmarks keyed to the anonymous id merge to the user once. Recorded trade-off: a vote's identity is the signed anon id, never the `source_hash`, so rolling the monthly hash salt cannot enable re-voting. The limitation is that clearing the anonymous cookie yields a fresh id and a fresh vote. This is inherent to voucher-free anonymous voting and is mitigated, not eliminated, by the `source_hash` submit rate limit and (M2) per-source vote limits. We accept it rather than force sign-in to vote.
- **Abuse control.** Layers in order: Turnstile, rate limit by `source_hash` and anonymous id, rule checks, model classification, flag auto-hide (three distinct sources), human review. Limits are config.
- **Self-harm safety floor.** Self-harm content must never be published (PRD FR-MOD-8, `Must`). M1 ships a conservative lexicon hold in the pure rule checks so such submissions are `held` and never reach any public read; the full safe-handling path (support-resources notice to the author) and model-based classification remain FR-MOD-4/FR-MOD-8 work in M2. The lexicon is a floor, not the final control: it is deliberately narrow to limit false positives and will be augmented, never replaced, by the M2 classifier.
- **Real-time.** In-process events go to a per-instance batcher (~1 s), which `pg_notify`s a compact payload; one dedicated direct connection per instance `LISTEN`s and feeds a hub of buffered per-client channels behind `GET /events` (SSE). Slow clients are dropped and resync. `REALTIME_MODE=memory` is a single-instance fallback.
- **Caching.** Hot reads go through a `Cache` interface (in-process TTL, Redis optional) wrapped in `singleflight` so a cold key runs one query. Read models (`country_stats`, hub counts) are refreshed on a schedule, never per request.
- **Privacy.** PII detection on input, hash-only network identifiers, deletion and export flows, consent gating for ads and analytics.
- **SEO.** `transport/web/seo` is the only place that builds titles, descriptions, canonicals, robots and JSON-LD, so the 5-pain threshold applies everywhere.
- **Observability.** Structured JSON logs with request ids, panic recovery, request-latency and job-outcome metrics, queue depth, moderation backlog, p95 latency.
- **Context and time.** Every I/O function takes `context.Context` first; timeouts on the server, outbound clients and per-call `statement_timeout`. A `Clock` is injected; ids are UUIDv7.
- **Configuration.** All environment variables are declared and validated in `internal/platform/config`; missing or invalid values fail startup.

## 11. Build and tooling

- **Taskfile, not Makefile.** `go-task` is pinned as a Go tool; every task is cross-platform. `task check` runs lint, vet, unit tests and build.
- **Tools via the `tool` directive.** `sqlc`, `goose`, `templ`, `govulncheck`, `air` and `task` are pinned in `go.mod`'s `tool` block and run with `go tool <name>`. `golangci-lint` is the exception: its own docs warn that `go tool` is unsupported, so it lives in a dedicated `golangci-lint.mod` module file (their documented `go tool` method) and CI uses the official `golangci/golangci-lint-action`.
- **Go version.** Pinned once in `go.mod`; CI reads it via `actions/setup-go` `go-version-file`, and the Dockerfile uses the matching `golang:<version>` image.
- **Tailwind fetch.** A small Go helper (`scripts/`) downloads the pinned standalone CLI asset for the current OS/arch from the Tailwind release, verifies its SHA-256 against a pinned lock file, caches it under `.cache/`, and execs it. The same helper runs on Windows, Linux CI and inside the Docker builder, so there is one code path and no Node.

## 12. Where to change what

| Task | Start in |
| --- | --- |
| Add a category | `internal/domain/taxonomy`, then hub copy |
| Change urgency weights | `internal/scoring/weights.go`, add a `scoring_versions` migration, write an ADR |
| Add a moderation rule | `internal/service/moderation` and its unit test |
| Add a page | `internal/transport/web` (handler + templ view + SEO entry) |
| Change a price | `internal/domain/billing/plans.go` only |
| Add a table | A new file in `db/migrations/`, plus its sqlc queries |
| Swap the model provider | The `internal/platform/llm` adapter; env model names |
| Bump the Tailwind CLI | `scripts/` lock file, then `task generate` |

## 13. What is deliberately not here

No microservices, message broker, service mesh, API gateway, per-service databases, GraphQL layer, native clients, user-to-user messaging or custom auth. Add one only with an ADR that names the problem the current design cannot solve and the measurement that justifies it.

## 14. Maintaining this file

Keep it under about 350 lines and in present tense. Update it when a module is added or removed, an invariant changes, or a boundary moves. Do not document function-level detail here; put that in code comments or `docs/`.
